# Laboratório do C3.5 — Transações e concorrência
- Ambiente (2026-11-25): PostgreSQL 17.12 (`c3-pg17`, 127.0.0.1:55432) e MySQL 8.4.13 (`c3-mysql84`, 127.0.0.1:53306), imagens oficiais; drivers Node.js `pg` 8.23.1 e `mysql2` 3.24.6. Sessões controladas por código (intercalação determinística com `await` e esperas curtas).
- Scripts: `pg-cenarios.cjs` (atomicidade, leitura suja/não repetível/fantasma, atualização perdida e 3 correções, write skew, deadlock, travas, MVCC, bloqueio otimista) → `saida-pg.txt`; `mysql-cenarios.cjs` → `saida-mysql.txt`; `pg-padroes.cjs` (savepoint, laço de repetição com 10 trabalhadores, advisory lock, pg_blocking_pids, transação longa x VACUUM) → `saida-pg-padroes.txt`; `pg-deadlock-ordem.cjs` → `saida-pg-deadlock-ordem.txt`; `pg-reservas.cjs` (20 tentativas simultâneas: ingênuo, EXCLUDE, trava consultiva, idempotência) → `saida-pg-reservas.txt`.
- Executar: `mkdir /tmp/c35 && cd /tmp/c35 && npm init -y && npm i pg@8 mysql2@3`, subir os contêineres (ver labs/postgres-mysql/README.md) e rodar `NODE_PATH=/tmp/c35/node_modules node pg-cenarios.cjs` (idem para os demais).
- Limitações: resultados de tempo e de contagem de repetições variam com a máquina e a ordem de execução (por exemplo, 49 tentativas e 39 repetições no laço de nova tentativa); o cenário SERIALIZABLE do MySQL foi sequenciado de forma simples (um UPDATE esperou até o tempo limite de 3 s) e em outras execuções pode terminar em deadlock; MySQL usa `innodb_lock_wait_timeout = 3` na sessão para acelerar os testes.
- Não executado: Group Replication, SHOW ENGINE INNODB STATUS, performance_schema, GET_LOCK, hot_standby_feedback e slots, wraparound de ids de transação, outbox com broker real.
