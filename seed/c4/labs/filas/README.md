# Laboratório: filas e processamento assíncrono (curso C4.5)

- Ambiente: Node.js 26.13.1, BullMQ 6.7.10, ioredis 6.1.0, pg 8.23.1, Redis 8.12.0 (`c4-redis`, `127.0.0.1:57379`) e PostgreSQL 17.12 (`c4-pg`, `127.0.0.1:55433`, só em `outbox.mjs`), em 2026-11-25.
- Reexecutar: `npm i`; `docker run -d --name c4-redis -p 127.0.0.1:57379:6379 redis:8`; `docker run -d --name c4-pg -e POSTGRES_PASSWORD=lab -p 127.0.0.1:55433:5432 postgres:17`; `node <script>.mjs` (os scripts limpam as filas que usam; `fila-basica.mjs` executa `FLUSHALL` no Redis do laboratório).
- Scripts e saídas: `fila-basica.mjs` (+ `filho-ingenua.mjs`, `filho-confiavel.mjs`, gerados) → perda de job ao cair o trabalhador em uma lista ingênua x BLMOVE; `bullmq-opcoes.mjs` → concorrência, prioridade, atraso, agendador, limitador de taxa e retenção; `retry-dlq.mjs` → backoff fixo x exponencial, backoff com jitter, DLQ, job travado (stalled) e idempotência; `outbox.mjs` → escrita dupla x outbox transacional, relay com SKIP LOCKED e consumidor idempotente.
- Correções feitas no laboratório: os scripts-filho do experimento de perda precisavam ficar no mesmo diretório para resolver `ioredis` (a primeira execução falhou por isso); o teste do job travado emitia erros "Missing lock" no stderr do worker e passou a capturá-los com `worker.on('error')`.
- Limitações: uma máquina e uma execução por medida (a forma importa mais que os milissegundos); os "trabalhadores que caem" são simulados com `process.exit` e com um laço síncrono, não com falhas reais de máquina; Redis único, sem persistência configurada para os testes (nada do laboratório garante durabilidade). Não executados: Redis em cluster e Sentinel com BullMQ, fluxos (flows) e jobs pai-filho, grupos de BullMQ Pro, RabbitMQ, Kafka, SQS, Sidekiq/Celery, cron em produção, métricas com Prometheus e o painel Bull Board.
